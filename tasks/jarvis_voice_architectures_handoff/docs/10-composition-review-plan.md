# Task10 — composition and admission review plan

Read-only preparation against current code, 2026-09-12. No implementation, status change, provider session or inference. Task09 types currently exist; its gate remains the orchestrator's responsibility. Names labelled **proposed** below are extensions to agree before coding, not existing APIs.

## Verified composition and exact target mapping

`app._run_voice_v2` still reads `voice_arch` / `JARVIS_VOICE_ARCH`, selects `v2_config.VoiceArchitecture`, and never calls `load_voice_architecture`. `RealtimeFrontendSession.connect` always constructs a `SimpleVoiceConfig` internally, although its actual instructions and VAD follow the legacy `continuous_brain` argument. That type label does not establish Simple behavior.

| Selection | Actual or required behavior |
|---|---|
| Compatibility metadata with `execution_mode=legacy` | Preserve current legacy path: existing rules/tools, Claude gateway, current turn lifecycle and supported Gemini behavior. Do not silently migrate it. |
| Compatibility metadata with `execution_mode=continuous_brain` | Preserve current continuous path: owner/echo capture, local interruption, Core `submit_brain_turn` for substantive admitted input, no surface tools, reflex-only instructions, backend result verbatim. |
| Explicit `SimpleVoiceConfig` without compatibility | New conversational frontend using its exact `conversation_model`. Admission and speech controls remain local. Admitted conversation can receive a substantive direct response without starting the strong backend. No Luna worker. |
| Explicit `FrontBrainVoiceConfig` without compatibility | The same conversational path using exact `reflex_model` (the name does not mean reflex-only), plus independent `analysis_model` through `FrontBrainAnalyzer`. Slow, unavailable or refused analysis leaves the Simple conversation path intact. |
| Explicit Duplex | Task12/13 implementation/readiness required. Task10 must reject unsupported activation rather than substitute Realtime. |

Use the existing versioned loader and `uses_compatibility_runtime` at the factory. Its migration projection intentionally retains old execution semantics; `store_voice_architecture` removes that compatibility metadata only for an explicit validated selection. Preserve inactive stack settings, credentials, chosen model IDs and existing compatibility behavior. New selection must resolve its model/provider first: an unrelated saved `voice_stack` must not override it. Reuse matching stack transport/audio options; reject unsupported provider/config combinations explicitly.

`voice_capabilities.default_voice_registry` currently marks Realtime entries `LEGACY_ONLY`, Luna `PLANNED`, and availability separately. Update readiness only for implemented/tested combinations, not merely because the configuration decodes. Google remains legacy-only until its canonical composition exists. Do not turn capability evidence into a claim of account availability.

## Why one existing boolean cannot implement this

The same `continuous` property currently chooses persistent capture, owner enforcement, scheduler creation, lifecycle after response, transcript filtering, uncertain-address routing, backend dispatch and closed tools. Setting it false for Simple loses owner/capture and installs the legacy gateway/automatic provider behavior. Setting it true forces all substantive turns into the backend.

Smallest change: one resolved composition value at startup, reusing the existing architecture enum/config rather than creating another architecture registry. Derive narrowly named runtime choices from it: continuous capture/session lifetime, local response admission, and admitted-turn destination (`legacy`, compatibility backend, direct conversation). Keep old constructor defaults for compatibility callers. Do not spread independent user-configurable flags through Settings. This is a necessary separation inside existing runtime/bridge, not a new controller framework.

New Simple/Front Brain should keep persistent conversation capture and local owner/echo/barge-in controls. Realtime VAD may segment input, but `create_response=false` and `interrupt_response=false` must be selectable independently of the reflex-only prompt. Local WAIT/noop means no request is sent. A Luna WAIT never delays an otherwise admitted, ready direct response. Auto-turn/manual-turn behavior needs an explicit supported choice; initially preserve automatic segmentation for the new continuous capture composition rather than claiming the legacy manual path is already equivalent.

## Minimum safe direct response path — new contracts required

1. **Existing local admission:** the bridge applies owner provenance before text addressing, noise/echo rejection and exact mute handling. Accepted final transcript then proceeds. Raw VAD, analysis permission and a provider ASR final are not, individually, final application admission. Existing compatibility `UNCERTAIN -> submit_brain_turn` must remain compatibility-only; for new modes use the existing deterministic WAIT/addressing policy unless a separate admitted conversational clarification is explicitly chosen. Luna confidence cannot grant admission.
2. **Proposed `LocalCoreClient.admit_voice_turn(...)`:** persist an admitted user turn and allocate/activate the existing durable `SpeechSource`, without dispatching backend work. Suggested endpoint `/v1/conversations/{conversation_id}/voice/admitted-turns`; input binds frontend session, canonical turn/transcript/revision, provider item, exact text and stable application correlation. Core owns turn/intent epoch and validates the bound canonical committed record; client cannot assign the epoch or submit a replacement snapshot. Return `{turn_id, correlation_id, source, duplicate}`. Admit the buffered canonical observation and flush its existing dispatcher before this validation; do not manufacture a provider commit.
3. **Proposed `SpeechScheduler.request_conversation(...)`:** a small direct-generation candidate holding the admitted input identity and returned `SpeechSource`, not a fabricated `SpeechRequest.text`, backend outcome or Job. Use the existing source freshness barrier, output serialization, `OutputAdmission`, invalidation and output-event accounting. Reserve one output ID, then recheck source/Stop after Core awaits and immediately before provider send. Expose that same token through `output_admission(output_id)` so `SoundDeviceRealtimeAudio` checks it at the first actual write. Current `_Candidate` / `_ActiveSpeech` hold a `SpeechRequest` with known text/chunks. Extending this existing candidate/active representation with a narrow conversation variant is required; no second queue, scheduler or output owner. The user prompt must never become intended assistant text or a semantic speech chunk.
4. **Proposed canonical `request_conversation(input_provider_id, *, operation)` and matching facade/low-level method:** request a substantive Realtime response using the already-present admitted input, session conversation instructions and the reserved output metadata. No user message reinsertion, verbatim instruction or reflex prompt. Return the same output identity; reserve/register correlation before awaiting network so an early provider event cannot escape binding. Cancelled/invalidated reservations remain invalid if provider creation arrives late.
5. Existing canonical assistant events, multipart manifest and checked native drain continue to establish generated versus heard evidence. Intended response text is unknown before generation: do not call `register_speech` with fake expected content. Do not count provider `response.done`, transcript final or local queue exhaustion as COMPLETE. Interruption remains governed by the bridge and real device evidence.

**What exists and what does not:** `ConversationService.append_turn` stores user history but creates a fresh ID by default and neither allocates a source nor dispatches work. Canonical `VoiceLedgerService` stores user observations but explicitly does not copy user history or dispatch. `BrainOrchestrator.submit` presently combines persistence, source allocation/activation, state revision and execution. SQLite `allocate_brain_source` / `activate_brain_source` already implement durable epoch and ownership checks; reuse them behind a neutral Core admission method, not a second source store. Extract the shared admission part so compatibility submission still executes exactly once, while new conversational admission never invokes a backend. Its retry/partial-persistence recovery must preserve stable turn identity, reject same-ID conflicting text and avoid reactivating an older source. Publish source context only after durable activation. Reuse the existing `speech_context()` payload schema; there is no standalone `speech.context` event today. The scheduler currently receives that payload through `BRAIN_TURN_ACCEPTED` / `BRAIN_INTENT_REVISED`. Add a narrowly named neutral admission event (proposed `voice.turn.admitted`) and its scheduler handler, or agree an equivalent ordered source notification; do not fake a backend-start event. Preserve the existing event-subscription/reconnect source barrier. Task11 later dispatches real work from an admitted source; it must not append that user turn again.

Existing `append_context_message(... request_response=True)` calls `append_message` then an uncorrelated `response.create`; it reinserts text and lacks the reservation contract. `finish_input` commits input again. `append_spoken_result` is verbatim and `request_reflex` uses the preamble replacement. None is the proposed direct-conversation operation. Do not hide this gap behind a compatibility shim.

The current adapter contains correlated `response.create` for speech/reflex, but no implementation of explicit input-item selection or rejected-input deletion. The official Realtime conversations guide confirms that `response.create.response.input` accepts existing conversation items as `{ "type": "item_reference", "id": "..." }`; it also confirms that VAD can keep segmentation while `create_response=false` and the client triggers responses manually. Use that documented input array to bind the already-present admitted provider item without reinserting its text. Do not set `conversation:"none"` for the normal conversational reply; that value is specifically out-of-band. Metadata still only correlates events and does not select model input. In particular, a newer or rejected provider item arriving before send must not silently become the request's subject. Keep the input reference list bounded, preserve admitted context deliberately, and test rejected-item contamination plus zero `conversation.item.create` writes. Source: https://developers.openai.com/api/docs/guides/realtime-conversations (manual responses and custom context sections, checked 2026-09-12).

## One canonical fan-out with item-bound analysis permission

The sole canonical reader is `RealtimeFrontendSession.events`: it calls `_observe(event)` then yields `_legacy_event(event)` to the bridge. `_observe` currently buffers `UserTurnOpened`/`UserTranscriptCommitted`, discards deltas for Core, and leaves final admission to `admit_transcript` / `discard_transcript`. This is the correct fan-out seam; neither Luna nor another task may consume `frontend.events()` a second time or read the raw provider socket.

The bridge owns `_admit_provider_segment` and the bounded `_segment_owner` provenance, after its `speech_started` processing. Capture already enforces the stronger pre-upload gate. A synchronous observer inside `_observe` cannot assume the bridge has processed the preceding owner event: its reader can run ahead of the control queue. `_segment_from_owner` also consumes the stored entry, so the sidecar must not call it as a second admission check. Never use `_last_segment_owner`, raw VAD or a current global owner state to bless an unrelated item.

Proposed narrow local interface on the sidecar coordinator, bound once per active session:

- `observe(event: VoiceEvent) -> None`: constant-time bounded update from the existing reader; no await/network and no new task per delta. Fold contiguous deltas into the latest full `VoiceUserRecord`, replace with authoritative final text/revision/commit source. Missing revision/order or overflow invalidates speculative analysis; do not guess missing text. This is a transient projection, not a second durable conversation store.
- `allow_item(provider_input_id, analysis_admission_id) -> None`: bridge grants a session/item-scoped application permission after positive upload/segment provenance, or the explicit open-room policy. Missing identity/provenance holds analysis. Buffered deltas may be considered only after this permission; transport access alone is not permission for another model.
- `reject_item(provider_input_id, reason) -> None` and `revoke_all(reason) -> None`: revoke pending/results/in-flight eligibility on known owner/address/noise rejection, ASR failure, session loss, Stop or configuration replacement. Keep bounded rejection identities so late events cannot re-create permission. At retention saturation, disable speculation for the incarnation rather than forgetting a still-relevant rejection. Do not revoke an admitted item merely because the current `_handle_transcript` finally calls `discard_transcript` to clean its buffer; distinguish cleanup from rejection explicitly.
- `admit_item(provider_input_id, source) -> None`: after Core admission, revise origin binding and schedule the budgeted final analysis. Before that point `origin_source=None` even when committed ASR text exists; current context source A may still be supplied separately for provisional B.
- `close()`: runtime owns worker, pending slot and cancellation; revoke synchronously before awaiting cleanup. A late reply cannot speak, dispatch, rearm timers or attach to a replacement session.

These method names are proposals, not a new public provider protocol. Reuse Task09 `FrontBrainAnalyzer.analyze`, `FrontBrainHintRequest`, `FrontBrainHintResult` and `FrontBrainHintConsumer` unchanged where possible. Populate request deadline/configuration/admission IDs in the application; provider returns only the strict value. Keep one in-flight request and one replaceable latest pending revision. Bounded cached Core context comes from the existing snapshot/source feed, not a per-delta HTTP call. Recheck current input, source completeness, revoked dependencies and permission at consumption.

Known-rejected input must never be newly submitted to Luna. Provisional addressing uncertainty is a different state: an explicitly permitted earlier analysis cannot be retroactively unsent, but its result becomes unusable once rejection is known. Document this distinction rather than promising that every eventually rejected utterance was never analyzed. Rejected provisional records need not enter Core at all in Task10.

## Prompt and hint integration

New Simple and Front Brain share a new explicit conversational rules builder layered with the existing JARVIS persona and bounded confirmed context. It must permit useful direct answers and honest limitations without saying that every request has already reached another brain. Do not select `CONTINUOUS_BRAIN_OPERATING_RULES`, and do not reuse legacy `OPERATING_RULES`, which require `claude_task` plus a preamble. Initially no legacy Claude gateway/action tools in the new path: Task11 owns actual work submission. A request requiring unavailable execution receives an honest conversational limitation, never invented progress.

Luna adds its own analysis prompt/config descriptor around the real Task09 schema. Its hypothesis/confidence/action remains data, not a replacement session instruction or user message. The smallest consumer uses accepted values as bounded advisory input to the existing deterministic controller; no fabricated work evidence for PREAMBLE, no execution for DELEGATE and no speech text from Luna. If consumption means only diagnostic acceptance initially, say so explicitly; do not claim it influenced conversation. Any prompt injection of accepted hints requires an explicit bounded data operation and TTL/removal design, not `session.update` per delta. Task15 owns the full inspector; Task10 exposes only actual builder IDs/defaults/config hooks.
