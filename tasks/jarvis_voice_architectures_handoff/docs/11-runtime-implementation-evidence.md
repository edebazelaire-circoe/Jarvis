# Task11 runtime execution and ownership

This subdelivery implements independent admitted-work execution over the existing Core JobService. Core owns authority, acceptance, queueing, source provenance, durable status/results and publication. Runtime owns exactly the CLI process resources it launches. Neither the worker nor its result decides speech.

## Configuration and entry points

`runtime/agent_settings.py` exposes `agent_defaults`, `resolve_agent_settings` and frozen `AgentExecutionSettings` via `resolve_agent_execution`. Control Center now delegates its existing resolution to the same pure functions: defaults/environment, legacy Claude fields, then structured `agent_cli_settings`. Provider, command, model and permissions are not accepted from a job request. `_run_core_v2` captures one settings snapshot at Core startup and registers `BackBrainJobWorker` under `back_brain`, alongside `memory_maintenance`. Pending jobs retain that snapshot even if the settings file changes; a Core restart applies new configuration. The cwd remains the configured application project root. Claude routing retains the existing hook and its runtime root; that hook still reads the current routing policy when a delegated tool is invoked. Codex has no invented equivalent.

`runtime/back_brain_worker.py::BackBrainJobWorker` implements `execute`, `execute_with_progress`, `cancel`, `cancel_owned` and neutral `cleanup_owned`. It consumes the strict shared `BackBrainWorkPayload` and returns `BackBrainResult`; no provider wire or speech object crosses this boundary. One owner occupies the worker's slot; Core queues other admitted jobs. A cleanup-pending owner keeps that slot occupied. Each job gets a fresh wrapper/session, never the Control Center singleton or its conversation lock. Input/context are bounded by the domain contract; results exceeding the 16384-character contract fail explicitly, without truncation or false completion.

`RealtimeFrontendSession.submit_back_brain(core, conversation_id, acceptance)` validates the typed admission/conversation pairing and sends only `acceptance.correlation_id` to the authenticated Core API. Submission returns the durable job reference independently of execution. Core's atomic acceptance reserves the original admitted turn so an old conversational backend submission cannot launch the same work. No text is reconstructed or recommitted by this seam.

The production caller is `runtime/back_brain_delegation.py::BackBrainDelegationController`, dispatched by the existing bridge's tool handler. Explicit Simple/Front Brain expose only the no-argument `back_brain_delegate` tool; compatibility tool catalogs remain unchanged. Conversation prompt `jarvis.conversation.v2` requires delegation before announcing long/uncertain work. The controller reserves the admitted source before the conversation response request, binds the provider response, then verifies the canonical call's session/local output/response/input/canonical turn/source correlation. It never substitutes the current Core turn or trusts model arguments. Unknown, invalidated or forged identity fails closed. Bounds are 128 operation/call identities, four asynchronous submissions and a ten-second submit deadline; no second provider reader or job executor is created.

After Core acceptance only, the controller enqueues a fixed `SYSTEM_NOTIFICATION` ACK through `SpeechScheduler.enqueue_controller_speech`: « Je m’en occupe. », exact source/correlation and `work_id=job_id`. A genuine unavailable response gets a short factual notice without a Job; loss of the acceptance response says only that acceptance cannot be confirmed. Duplicate calls for the same source/job do not repeat the ACK. Scheduler freshness, TTL and first-write admission remain authoritative; an old ACK cannot start after a new source. Tool result delivery uses `request_response=False`, so no unregistered raw response continuation bypasses those gates. Generated ACK text is not heard history until device playback proves it. Closing the frontend cancels only local submission transport, never a durably accepted Core job. Job completion produces no speech.

`speculative_analysis` is rejected before configuration/factory/spawn. Result-only prompts are not a sandbox. Decision22's restricted speculative executor remains unavailable.

## Result profile and lifecycle

Claude's default `conversation` profile remains unchanged. The explicit `job_result` profile replaces `BRAIN_SYSTEM_PROMPT` with `JOB_RESULT_SYSTEM_PROMPT`, removes automatic Chrome attachment and retains selected model, permissions and routing. It instructs the executor to finish and collect delegated work before returning its complete result, rather than ending with the conversational coordinator's acknowledgement. Only correlated terminal CLI result events become job results; assistant preambles do not complete the job. This tests protocol behavior and prompt selection, not live model obedience.

Both wrappers expose permanent `close_owned` and `wait_started` for dedicated job instances. Permanent closure is set before awaiting the spawn lock. A pending spawn publishes its handle before cleanup; later starts are rejected. The worker shields its execution task from caller cancellation until its owned cleanup has terminated native execution. Repeated cancellation preserves `CancelledError` and joins the same cleanup task. Wrapper stop/start defaults remain available to existing conversational callers.

A valid result remains local to the owned execution while native cleanup is pending. The worker reports `cleanup_pending` once, retries at bounded cadence and returns the original result only after closure confirmation. It does not turn a slow natural close into FAILED or infer a cancellation. `cleanup_owned` is neutral; `cancel_owned` records an actual cancellation. Core retains its slot and handles durable finalization separately.

`runtime/owned_process_tree.py` supplies Windows Job Object ownership. Job-only subprocesses launch with `CREATE_SUSPENDED | CREATE_NO_WINDOW`. The job disallows breakaway, attaches the suspended root, then resumes its thread using documented Toolhelp/OpenThread/ResumeThread calls. `TerminateJobObject` precedes root/reader joins; `ActiveProcesses == 0` and successful handle close are required for confirmation. Root exit alone is insufficient. Assignment/resume failure keeps the suspended process recoverable for cleanup; failed handle close stays retryable. Cleanup exceptions preserve an existing primary exception. No interactive console, shell-composed task text or actual agent CLI is used by tests.

Microsoft documents the [Job Object lifetime and child inheritance](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) and the [suspended-create, assign, resume sequence](https://devblogs.microsoft.com/oldnewthing/20131209-00/?p=2433). The guarantee covers processes owned by that Job Object. It does not undo completed actions, cancel remote services or claim confinement of privileged processes launched through external service brokers. Unsupported platforms or failure to establish ownership fail explicitly. A host crash between suspended process creation and assignment remains a narrow possible suspended-root leak; no task instructions have executed in that window. Core recovery does not silently rerun interrupted jobs.

## Observability and tests

RuntimeJournal normal sequence is `job.agent.owned` → `job.agent.started` → `job.agent.finalizing` → `job.agent.closed` → `job.agent.result`. Records carry job/conversation/source correlation and configured provider/model. `agent_started` progress is emitted only after actual spawn/attachment, and `finalizing` before cleanup/result. Progress contains no raw CLI text, fraction estimate or speech instruction; Core persists/publishes it through its existing typed progress sink and cadence policy.

Failure diagnostics use `job.agent.failed` with stable `back_brain_execution_failed`, `back_brain_invalid_result` or `back_brain_timeout` codes. Recoverable cleanup emits `job.agent.cleanup` with `back_brain_cleanup_pending` or `back_brain_cleanup_failed`. No result is emitted before cleanup confirmation. Worker and dedicated wrapper journal failures are best effort, contained without recursive logging; unavailable diagnostics cannot change a business result or break a reader/cleanup. The dedicated wrapper journal forwards only safe lifecycle kinds, omitting raw prompts, output, reasoning, tool events and stderr; compatibility wrapper logging is unchanged. Controller `voice.back_brain.delegation` records status/job/source only. No temporary probes were added.
