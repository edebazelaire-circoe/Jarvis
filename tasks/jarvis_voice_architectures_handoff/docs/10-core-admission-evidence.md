# Task10 — Core admission implementation evidence

Implementation scope only; no slice/status validation. No provider session or model inference. Existing Task08 work in shared files is preserved.

## Contract

`VoiceTurnAdmissionRequest` schema 1 binds conversation, frontend session, canonical turn/transcript/revision, exact text, provider item and `addressing` (`addressed` or `uncertain`). IDs use the existing printable 256-character bound; text is nonempty valid Unicode up to 8,192 characters; revision is a nonnegative signed-64-bit integer. Unknown/missing fields, booleans as integers, duplicate JSON keys and nonfinite/wrong-typed numbers fail. HTTP bodies are bounded to 65,536 bytes. No application correlation, epoch, replacement snapshot or transport source is accepted from the client.

`LocalCoreClient.admit_voice_turn(conversation_id, *, text, addressing, session_id, canonical_turn_id, transcript_id, transcript_revision, provider_item_id)` returns typed `VoiceTurnAdmissionAcceptance`. POST `/v1/conversations/{conversation_id}/voice/admitted-turns` uses existing authenticated loopback middleware and health refusal. Body includes version and conversation identity; route/body disagreement fails.

Core derives `voice-source-` + `stable_identity(conversation_id, session_id, canonical_turn_id)`. The persisted USER ID is `brain-turn-` + `stable_identity(conversation_id, correlation_id)`, shared with subsequent backend ingress. Acceptance carries this source, turn ID, correlation and duplicate flag. Canonical turn, Core turn and Core correlation remain different namespaces.

`VoiceLedgerService.checkpoint_admitted_input` validates a current server-owned committed record under the ledger lock: session, canonical turn, transcript/revision, exact text and provider input all match. It saves that server snapshot before admission and returns its exact `VoiceTurnOrder`. It cannot accept a client snapshot/order or turn a provisional record into committed evidence.

## Durability and ownership

`VoiceTurnAdmissionService` shares `BrainOrchestrator`'s lock. Its common `persist_turn` validates existing immutable input, repairs the same history record by ID, then allocates the existing repository `SpeechSource`. Direct admission activates only addressed input. Every activation also requires the existing monotone epoch guard and, for direct sources, ordering evidence from the durable server canonical checkpoint: predecessor links take precedence over server observation order. Admission HTTP order is not input order. A first delayed admission of older A, its retry, later backend submission or uncertain promotion cannot replace B merely because A received a larger allocation epoch. Missing evidence or disagreement between canonical order and epoch refuses activation. Uncertain input gets a durable origin but leaves current source unchanged. The process-local brain intent projection follows an actual activation without starting a task.

The ledger checkpoint, USER/history persistence and source allocation/activation are separate recovery steps, not a cross-store transaction. Checkpoint-only, history failure and allocation failure are exercised through a real SQLite restart. A duplicate resumes the same identities; it does not append another USER record or allocate another epoch. Window eviction alone does not erase an admitted USER's persisted server order. Missing or incompatible evidence still fails conservatively.

`voice.turn.admitted` publishes the acceptance after durability. `brain.source.changed` publishes exactly `BrainOutcomeService.context` when the accepted source is current. This includes an idempotent replay on retry, recovering publication failure after durable activation. If B has superseded A, retrying A publishes its admission acceptance but never a source-change event for A. Repeating the current projection does not allocate a new epoch or activate again. Neither is backend work or speech evidence. The normal `core.voice.turn_admitted` diagnostic contains identities, duplicate and activation flags, never transcript text. Request repr also excludes text. Validation and storage failures propagate; no successful admission is fabricated.

`BrainOrchestrator.submit` reuses persistence/source ownership. A later backend submission of direct-admitted A must retain A's origin while current B stays current. Existing compatibility addressing/uncertain behavior and output retention remain in place. Admission itself has no backend, Job, speech request or action invocation.

Dispatch is a separate reservation boundary. Exactly-once side effects across a process crash cannot be established by a marker: a crash after durable reservation and before actual launch must not trigger an automatic duplicate run. Task11 owns explicit job recovery. The dedicated `claim_admitted_backend_dispatch(turn_id)` validates a complete versioned binding against the stored USER, conversation, exact text, derived correlation/turn IDs, source/addressing/provider metadata, durable source and server canonical checkpoint. An arbitrary metadata object is insufficient. It then uses a conditional UPDATE restricted to that direct-admitted USER without a reservation marker, returns its rowcount, and commits before return. Two independent SQLite connections competing for the same turn produce exactly one successful reservation. Only the reservation metadata changes; text, identity, source and archive are unchanged. Ordinary `save_turn` uses INSERT OR IGNORE and is no longer used to claim dispatch.

## Independent review correction F4 — order survives window eviction

The reviewer's next test reproduced a current source frozen after more than 128 chained uncertain admissions evicted its canonical order from the bounded snapshot. The fix persists a constant-size, server-derived `voice_admission_order` alongside the existing admitted USER metadata: schema version 1, session, canonical turn, predecessor and server observation ordinal. The checkpoint supplies this proof; the HTTP schema rejects an injected order. Retry requires the same proof, and dispatch claims validate it against the full immutable admission and available server checkpoint. Missing or corrupt metadata is not silently backfilled.

Source activation resolves evicted ancestors from existing USER rows using their stable canonical binding. It adds no lineage table or alternate store. The traversal is iterative, runs in the existing SQLite worker inside the activation transaction, and has no arbitrary depth ceiling. It stops at a direct ancestry join, root or missing record; visited sets detect cycles without quadratic path membership scans. Proof storage is fixed per USER; traversal time and temporary memory grow with the ancestry examined, so this is not a constant-time query or a hard lock-latency guarantee.

Explicit predecessor ancestry remains stronger than the server observation ordinal. Siblings with a common ancestor cannot promote each other, including when those parents have left the snapshot. Missing explicit predecessors, cycles, malformed bindings and conflicting proof fail closed. Observation order is only a fallback for complete, nonintersecting root paths; an allocation epoch never substitutes for canonical evidence. Admission, subsequent backend submission and uncertain-result promotion all retain the same activation authority and monotone epoch guard.

Added verification covers a 400-turn linear chain (more than 256 ancestors beyond the bounded window) with restart and successful subsequent addressed activation; restart variants through backend submission and actual uncertain promotion; forks whose parents were evicted; missing and cyclic durable ancestry; ten malformed or forged order variants refused at dispatch claim; and client order injection refusal. The 400-turn case completes normally with no blocked wait. The reviewer-owned file remains unchanged.
