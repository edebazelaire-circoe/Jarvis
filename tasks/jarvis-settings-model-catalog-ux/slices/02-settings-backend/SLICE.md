# Slice 02 — Persist and expose Agent/CLI technical + personality options

## Goal

Implement/migrate backend settings and APIs for the new Agent/CLI configuration without breaking existing routing policy.

## Context

Current routing settings/backend already exist. The user-facing IA changes, but the runtime must keep policy enforcement and saved preferences.

## Canonical Concepts

- Auto/Dupliqué setting bound to live delegation semantics
- supported technical options from Slice 01
- verbosity/politeness and supported behavior options
- migration from old routing UI state
- API validation/defaults

## Scope

### In Scope

- Add/rename settings fields using canonical contracts.
- Preserve existing allowlists/preferences and routing hook behavior.
- Expose structured settings metadata to the UI where practical.

### Out of Scope

- Catalog table rendering.
- Voice UI tabs.

## Implementation Steps

1. Implement backward-compatible config migration/aliases.
2. Wire Auto/Dupliqué to the existing delegation mechanism or implement the audited missing contract once, centrally.
3. Add supported technical fields with validation/defaults.
4. Add behavior/personality fields only where a consumer exists; otherwise defer.
5. Expose APIs and tests.

- Settings allowlists/availability continue to override model names generated by an LLM.
- UI migration must not silently enable routing/policy that was previously disabled.

## Acceptance Criteria

- Existing routing behavior remains stable unless the user changes new settings.
- Auto/Dupliqué persists and affects exactly one canonical runtime path.
- Old saved preferences survive migration.
